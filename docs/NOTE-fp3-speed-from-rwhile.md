# なぜ fp3 が rwhile-C-ocaml では速いのか — 隣の rwhile 側からの調査メモ

2026-06-19、rwhile-C-ocaml（横山研）側の調査より。while-C の fp3（cogen）が ~2h なのに rwhile では
fp2/fp3 が ~18s で済む理由を、両者を実測して切り分けました。**結論を先に：主因は「rwhile の自己適用が
ほぼ自明（spec を最適化せず凍結するだけ）」で、while-C より特殊化の仕事を少なくしているためです。**
fp 等式は両者とも正しく成立しますが、「同じ量の特殊化」をしている head-to-head ではありません。

## まず訂正（最初の直感は誤り）

「rwhile はネイティブ実行、while-C は万能プログラム `u` 経由だから遅い」は**誤り**です。while-C には
`src/core/RunData.ml`（`rundata`＝プログラム・アズ・データのネイティブ実行器、rwhile の `d2p` 相当）が既にあり、
残余の実行方法は主因ではありません。

## 決定的な証拠：出力サイズの「署名」

対象インタプリタは対等（`ri_min` と `int_min` は同一の最小インタプリタ：1分岐 `if =? Op 'swap`、ループ無し）。
差は**特殊化器の挙動**にあり、出力サイズに表れます。

| 量 | rwhile-C-ocaml | while-C-ocaml |
|---|---|---|
| spec 本体 | spec_av(p2d) **817,701 ノード** | ⌜mix⌝ **2.48 MB** |
| fp2 `comp2 = [spec]((spec.int))` | **812,515 ノード ≈ 1×|spec|** | （~42 min） |
| fp3 `cogen = [spec]((spec.spec))` | **1,630,121 ノード ≈ 2×|spec|** | **29.6 MB ≈ 12×|mix|** |
| cogen 構築 | **18.3 s、peak RSS 99 MB** | **~2 h、peak RSS 1.68 GB** |

- **rwhile**：`[spec](spec, X)` の出力が「spec を X 込みで凍結しただけ」のサイズ（comp2≈1×、comp3≈2×）。
  これは Jones のいう **自明なスペシャライザ**（埋め込むだけ・自己最適化しない）の署名そのもの。
  特に `comp2`（int 用コンパイラ）が **spec とほぼ同サイズ** ＝ spec の解釈オーバヘッドを自己最適化で
  消せておらず、生成コンパイラは spec まるごとを抱え、`[comp2]('S.op)` は実質 fp1 を毎回やり直すだけ
  （＝コンパイラ生成の高速化メリットが無い）。だから cogen 構築が安い（コピー＋凍結）＝速い。
- **while-C**：cogen が mix の **~12×** ＝ mix は自己適用で実際に展開/特殊化している（＋既知の no-op bloat）。
  本来難しい「最適化する自己適用可能 PE」をやっているので高コスト。

## これは「不正」ではない（が「対等」でもない）

- rwhile が自明寄りなのは **IEICE 親論文の設計どおり**で開示済み：「rspec は文献[Jones97]の自明な
  スペシャライザ（最適化を行わないもの）の可逆版。生成プログラムの効率化（定数伝播・事前計算）は今後の課題」。
- 両者とも fp1/2/3 は正しく成立（残余は正答）。rwhile も**対象レベルでは最適化**している
  （`[spec_av]((ri_min.swap))` は 163→103 ノード＝静的ディスパッチ除去）。
- while-C の遅さの一部は no-op bloat（無駄）だが、一部は本物の特殊化仕事。

## まとめ

「fp3 実行時間」での head-to-head は対等な効率ベンチではありません。rwhile が速いのは
**(1) 自己適用がほぼ自明（spec を自己最適化せず凍結＝やる仕事が少ない、IEICE 設計どおり）** が主因、
加えて **(2) 実装の定数倍が軽く中間 bloat も少ない**（comp3 が 2× で収まる／peak 99 MB）。
while-C は「最適化する PE」という難しい方に挑んでいるため、自己適用が 12× に展開し ~2h・1.68 GB になります。

### 補足（構築コスト側）
副次的に、while-C 側は peak 1.68 GB から **アロケーション/GC 量**も効いている疑い（no-op bloat した中間を
連想リストストア `type store=(id*valT) list` が代入ごとに O(n) コピー）。ただし rwhile も同じ連想リストで
18s/99MB なので、ストア構造そのものは主因でなく、**展開量（12× vs 2×）と総アロケーションの差**が本質です。
